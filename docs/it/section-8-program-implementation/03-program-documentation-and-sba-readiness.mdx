## 1. Why Program Documentation Matters! (Syllabus Objective 8.6!)

Writing a working program is only **half the job**! Six months later — when Jamaica changes its GCT rate, a bug pops up, or a brand-new programmer joins the company — undocumented spaghetti code is almost impossible to understand safely!

**Program Documentation** is all the written explanations, formatting, and guides accompanying a program to make it **easy to read, debug, update (maintain), and operate**! It splits cleanly into **TWO essential halves**:

## 2. Internal Documentation vs External Documentation

### A. Internal Documentation *(Built DIRECTLY INSIDE the Source Code — for Programmers!)*
Internal documentation is read by **developers and examiners inspecting the code** (and is ignored by the computer when running the program!):

| Internal Feature | What It Means | Poor Example ❌ | Clean, Full-Mark Example ✅ |
| :--- | :--- | :--- | :--- |
| **1. Mnemonic (Meaningful) Variable Names** | Naming variables & constants so they describe **exactly what data they store**! | `a`, `b`, `c`, `x1` | `itemPrice`, `studentCount`, `GCT_RATE`, `netPay` |
| **2. Comments** *(Header & Inline)* | Plain-English notes explaining **Author, Date, Purpose** at the top + tricky logic inside — completely **ignored by the compiler/interpreter**! | No comments anywhere | Pascal: `{ Compute 10% bulk discount }`<br/>Python: `# Compute 10% bulk discount`<br/>C: `// Compute 10% bulk discount` |
| **3. Indentation** | Shifting code blocks cleanly right (2–4 spaces) inside every **`IF`**, **`ELSE`**, **`FOR`**, and **`WHILE`** block so program structure pops visually! | Every single line jammed flush against the left margin! | Clearly indented nested loops and `if/else` branches! |
| **4. Effective Use of White Space** | Leaving **blank lines** between logical sections (declarations, input block, processing loop, final output) and spaces around operators! | 40 cramped lines smashed together with zero blank lines! | Blank lines cleanly separating Init, Input, Calculation, and Output blocks! |

### B. External Documentation *(Separate Written Guides — for End Users & Technicians!)*
1. **User Manual (User Guide):** Written in **clear, non-technical everyday language** for the everyday person operating the program! Includes:
   - **Purpose & Overview** of what the software does,
   - **System Requirements** (minimum OS, RAM, disk space),
   - **Installation & Startup Steps** (with clear screenshots!),
   - **Step-by-Step Operating Instructions** (how to enter data, sample screens, sample valid inputs & outputs),
   - **Troubleshooting / FAQ & Error Messages** (what to do if an error pops up, plus help-desk contact details)!
2. **Technical / Programmer Manual:** Written for IT maintenance staff — contains the **Problem Statement, IPO Chart, Flowcharts/Pseudocode, Data Dictionary, Complete Commented Source Code, and Trace Table / Test Plan**!

## 3. Worked Example: Auditing Poorly Documented Code (Paper 2!)

<WorkedExample
  title="Fixing Internal Documentation & Distinguishing Internal vs External Guides"
  marks={6}
  problem={
    <>
      Look at this poorly documented snippet written by a classmate:
      <br />
      <code>a=0</code><br />
      <code>b=int(input())</code><br />
      <code>while b&gt;0:</code><br />
      <code>a=a+b</code><br />
      <code>b=int(input())</code><br />
      <code>print(a)</code>
      <br />
      (a) Identify <strong>THREE</strong> internal documentation flaws in the snippet above and rewrite it properly in Python.
      <br />
      (b) Explain clearly why a non-technical school bursar needs a <strong>User Manual (External Documentation)</strong> rather than just reading the commented source code.
    </>
  }
  examTip="Always cite the exact 4 official internal documentation terms from the syllabus: (1) Mnemonic variable names, (2) Comments (author/date/purpose), (3) Proper Indentation, and (4) Effective White Space!"
>

### (a) Three Flaws & Cleanly Documented Rewrite
- **Flaws:** (1) Cryptic non-mnemonic names `a` and `b`; (2) Zero comments explaining author/date/purpose; (3) Missing indentation inside the `while` loop (causes a Python syntax error too!) & no white space separating logical blocks!

```python
# Program: Positive Sales Accumulator
# Author : K. Campbell | Date: 16 Nov 2026
# Purpose: Sums positive sales amounts until a zero/negative sentinel is entered

total_sales = 0

sale_amount = int(input("Enter sale amount (0 or negative to stop): "))

while sale_amount > 0:
    total_sales = total_sales + sale_amount
    sale_amount = int(input("Enter next sale amount (0 or negative to stop): "))

print("Total Sales: J$", total_sales)
```

### (b) Why the Bursar Needs External Documentation (User Manual)
- The bursar is an **end user, NOT a programmer** — they should never have to read source code! A **User Manual** gives plain-English step-by-step instructions, sample inputs, screenshots, and error troubleshooting so staff can operate the program accurately and safely!

</WorkedExample>

## 4. Complete 50-Mark IT SBA Readiness Checklist (All 5 Components!)
