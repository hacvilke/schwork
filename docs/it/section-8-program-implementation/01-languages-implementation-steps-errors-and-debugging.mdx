## 1. Low-Level vs High-Level Programming Languages (Syllabus Obj 8.1!)

CPUs ONLY understand raw binary **`0`s and `1`s** (**Machine Code**). Humans write programs at different levels of closeness to hardware:

| Feature | **Low-Level Languages** *(Machine Code & Assembly Language)* | **High-Level Languages** *(Pascal, C, Visual Basic / VBA, Python, Java)* |
| :--- | :--- | :--- |
| **How It Looks** | • **Machine Code (1st Gen):** Pure binary (`10110000 01100001`).<br/>• **Assembly (2nd Gen):** Short hardware mnemonics (`MOV AX, 5`, `ADD AX, BX`). | Readable English-like statements & familiar math (`IF score >= 50 THEN`, `total = price * qty`)! |
| **Portability** | **Machine-dependent** — tied strictly to one CPU architecture (won't run on a different chip!). | **Portable (Machine-independent)** — same source code can be compiled/run across Windows, Mac, and Linux! |
| **Speed & Memory** | **Ultra-fast execution & tiny memory footprint** (direct hardware control — used in OS kernels, device drivers, embedded chips!). | Slightly slower than hand-tuned assembly, **BUT** massively faster & easier for humans to **write, read, debug, and maintain**! |
| **Translator Needed?** | Machine Code needs **NO translator**; Assembly uses an **Assembler**! | MUST be translated into machine code by a **Compiler** or **Interpreter**! |

*(Quick bonus on Generations: **1GL** = Machine Code; **2GL** = Assembly; **3GL** = Procedural High-Level like Pascal, C, Python, VB; **4GL** = Non-procedural / Declarative like **SQL**; **5GL** = AI / Logic / Natural Language constraint systems!)*

## 2. Language Translators: Assembler vs Compiler vs Interpreter

| Translator | Translates… | How It Works | Pros & Cons |
| :--- | :--- | :--- | :--- |
| **Assembler** | **Assembly Language** → Machine Code | Converts low-level mnemonics (`LOAD`, `ADD`) one-to-one into binary machine instructions. | Tiny, ultra-fast output; hard for humans to write big apps. |
| **Compiler** *(used by Pascal, C, C++)* | Entire **High-Level Source Code** → **Object Code / Executable (`.exe`)** ALL AT ONCE! | Scans the whole program, lists **ALL syntax errors together**, and once error-free links libraries into a standalone executable file! | **Fastest runtime execution** (no need to re-translate every run, hides source code!); **slower edit-test cycle** (must fix all syntax errors before running). |
| **Interpreter** *(used by Python, JavaScript, VBA)* | High-Level Source Code **ONE LINE AT A TIME** during execution! | Reads Line 1 → translates → executes immediately → moves to Line 2; **stops immediately** at the first syntax error! | **Super easy debugging & fast prototyping**; **slower execution** because every line re-translates every time it runs (including inside loops!), and user must have the interpreter installed! |

## 3. Four Steps in Implementing a Program (Syllabus Objective 8.2!)

Once your algorithm (flowchart/pseudocode) is verified in Section 7, turning it into a real working application follows **FOUR official steps**:

1. **Create Source Code:** Type the program instructions carefully in a code editor/IDE (e.g. Free Pascal, IDLE/VS Code for Python, Code::Blocks for C, or Excel's VBA Editor) following exact language syntax rules!
2. **Translate and/or Link:** Run the **Compiler** (which converts source code into **Object Code** and **Links** built-in libraries into an executable file — on interpreted/modern IDE systems like Python/VBA this happens transparently behind the scenes!). Fix any **Syntax Errors** flagged here!
3. **Execute (Run) the Program:** Run the program with carefully selected **test data** (valid, boundary, and invalid inputs!), verify screen outputs against your Trace Table, and fix any **Runtime** or **Logic Errors**!
4. **Maintain the Program:** Update and support the deployed program over its lifetime — fixing newly discovered bugs, adapting to rule changes (e.g. if Jamaica's GCT rate or PAYE threshold changes!), or adding requested features!

## 4. The Three Types of Program Errors (**Guaranteed Paper 1 & 2 Marks!**)

Every programming bug falls into **ONE of three exact categories** — know **WHO catches it**, **WHEN it happens**, and a **concrete example**!

| Error Type | Exact Definition | When Caught & Does Program Run? | Concrete Exam Examples |
| :--- | :--- | :--- | :--- |
| **1. Syntax Error** | Violates the **grammar / spelling / punctuation rules** of the programming language! | Caught **BEFORE execution** by the **Compiler/Interpreter** → **Program WILL NOT RUN!** | Misspelling `WRITELN` as `WRITLN`, missing a semicolon `;` in Pascal/C, missing a colon `:` or unmatched bracket `)` in Python! |
| **2. Runtime Error** | Syntax is valid so the program starts running, **BUT crashes / halts abnormally mid-execution** due to an impossible operation! | Caught **DURING execution** → **Program CRASHES mid-run!** | **Division by zero** (`Total / 0`), typing text `"abc"` into an **Integer** variable, accessing an out-of-bounds array slot, or opening a missing file! |
| **3. Logic Error** *(Hardest to catch!)* | Program has valid syntax and runs smoothly to completion without crashing, **BUT produces the WRONG answer** due to flawed human design/formula! | **NEVER caught by the compiler!** Caught ONLY by **human testing & Trace Tables**! | Writing `Avg = A + B / 2` instead of `(A + B) / 2`; using `>` instead of `>=` on a `50` pass mark; subtracting discount instead of adding tax; or causing an **infinite loop**! |

## 5. Testing (Test Data) & Debugging Techniques (Syllabus Obj 8.3!)

**Debugging** is the systematic process of **locating, diagnosing, and fixing errors (bugs)** in a program!

### Three Essential Types of Test Data (Test Thoroughly!)
For an algorithm accepting exam scores **`0` to `100`** (Pass ≥ `50`):
1. **Normal (Typical Valid) Data:** Ordinary expected inputs (e.g. `72`, `35`).
2. **Boundary (Extreme) Data:** Exact edge values right on the limits (`0`, `49`, **`50`**, `100`) — catches sneaky `>` vs `>=` logic errors immediately!
3. **Erroneous (Invalid) Data:** Out-of-range or wrong-type inputs (`-5`, `105`, `"eighty"`) — proves your validation rejects bad data safely without crashing!

### Practical Debugging Techniques
- **Dry Run / Trace Table:** Walk through tricky loops by hand on paper comparing variable values step by step!
- **Print / Watch Statements:** Temporarily print intermediate variable values inside loops to see *exactly* where a calculation went wrong!
- **IDE Debugger Breakpoints & Stepping:** Pause the running code line by line (`Step Over` / `Step Into`) to inspect live RAM variables!
- **Reading Compiler Error Messages & Line Numbers:** Start fixing from the **FIRST (topmost)** syntax error — one missing semicolon often triggers 5 fake cascade errors below it!

## 6. Worked Example: Identifying Error Types & Selecting Test Data (Paper 2!)

<WorkedExample
  title="Diagnosing Syntax, Runtime & Logic Errors in a Student Grading Program"
  marks={8}
  problem={
    <>
      A student writes a short program to average <code>N</code> test scores (valid scores <code>0–100</code>; Pass if Average ≥ <code>50</code>):
      <br />
      (i) Line 4 reads <code>PRNT("Enter count of tests:")</code> — the translator rejects it before running.
      <br />
      (ii) After fixing Line 4, the user enters <code>N = 0</code>; the program runs to <code>Average = Total / N</code> and immediately crashes!
      <br />
      (iii) After preventing <code>N = 0</code>, the student enters scores <code>50</code> and <code>50</code> (Average = <code>50</code>), and the program runs cleanly to completion — but prints <strong><code>"Fail"</code></strong> because the code wrote <code>IF Average &gt; 50 THEN</code>!
      <br />
      (a) Classify the exact error type in <strong>(i)</strong>, <strong>(ii)</strong>, and <strong>(iii)</strong>.
      <br />
      (b) Explain how to fix error <strong>(iii)</strong> AND name <strong>ONE example each</strong> of Normal, Boundary, and Erroneous test data for this program!
    </>
  }
  examTip="Notice how EVERY error type leaves an unmistakable clue: 'rejected before running' = Syntax; 'starts running then crashes on / 0' = Runtime; 'runs cleanly to end but prints wrong result' = Logic!"
>

### (a) Classifying All Three Errors
- **(i) `PRNT(...)` rejected before running:** **Syntax Error** *(misspelled keyword violates language grammar rules)*.
- **(ii) Crashes on `Total / 0` mid-run:** **Runtime Error** *(illegal division by zero during execution)*.
- **(iii) Prints `"Fail"` for Average `50` cleanly without crashing:** **Logic Error** *(flawed condition `>` instead of `>=`)*.

### (b) Fixing (iii) & Choosing Test Data
- **Fix for (iii):** Change `IF Average > 50 THEN` to **`IF Average >= 50 THEN`**!
- **Test Data Examples:**
  - **Normal Data:** `65` and `75` *(expects `"Pass"`)*
  - **Boundary Data:** `50` *(exact pass threshold)*, `49`, `0`, `100`
  - **Erroneous Data:** `-10`, `120`, or `"fifty"` *(tests safe rejection / validation!)*

</WorkedExample>
