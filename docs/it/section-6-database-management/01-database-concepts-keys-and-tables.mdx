## 1. What Is a Database & Why Use a DBMS?

A **Database** is an **organised, structured repository of information** — specifically, in a **Relational Database Management System (DBMS)** like **Microsoft Access** or **LibreOffice Base**, it is a **collection of tables that are related to each other**!

### Why Organisations Replace Paper Filing Cabinets With a Digital DBMS
1. **Instant Searching & Sorting:** Locate one student or patient out of 50,000 records in milliseconds instead of digging through steel cabinets!
2. **Reduced Data Redundancy & Inconsistency:** By splitting related data across linked tables (e.g. storing a customer's address ONCE in a `CUSTOMERS` table instead of repeating it on 100 separate order sheets!), updating an address in ONE spot automatically updates everywhere!
3. **Stronger Data Integrity & Validation:** Built-in field data types, primary keys, and input rules stop invalid/duplicate records from being entered.
4. **Security & Controlled Multi-User Access:** Password logins, user role permissions, and fast digital backups protect records from fire, theft, or unauthorised viewing.

## 2. Core Database Terminology & The Four Key Types (**HUGE Paper 1 & 2 Topic!**)

Look at this `STUDENT` table in a Jamaican school database:

| `StudentID` *(PK)* | `TRN` | `FirstName` | `LastName` | `Parish` | `HouseCode` *(FK)* |
| :---: | :---: | :--- | :--- | :--- | :---: |
| `STU001` | `124-555-801` | Aaliyah | Brown | St Catherine | `H01` |
| `STU002` | `129-440-219` | Devon | Reid | Kingston | `H02` |
| `STU003` | `131-882-045` | Shanice | Brown | St Catherine | `H01` |

- **Table (Relation / Entity):** Organised grid storing data about ONE type of thing (`STUDENT`, `HOUSE`, `ORDER`).
- **Record (Row / Tuple):** All the data about **ONE single item/person** horizontally (e.g. `STU001 | 124-555-801 | Aaliyah | Brown | St Catherine | H01`).
- **Field (Column / Attribute):** **ONE specific category of data** stored for every record vertically (`StudentID`, `LastName`, `Parish`).

### Distinguishing All FOUR Key Types (Memorise Every Exact Definition!)

| Key Type | Exact Exam Definition | Example in `STUDENT` Above |
| :--- | :--- | :--- |
| **1. Primary Key (PK)** | A field (or combination of fields = *Composite Key*) that **UNIQUELY identifies every single record** in a table! **Cannot contain duplicates AND cannot be blank (`NULL`)!** | **`StudentID`** *(Why NOT `LastName`? Two students are named `"Brown"`!)* |
| **2. Candidate Key** | **ANY field** in a table that *could* qualify to be chosen as the Primary Key because every value is unique and non-null! *(One candidate key gets picked as the Primary Key; the leftover ones are alternate keys!)* | **Both `StudentID` AND `TRN`** are Candidate Keys! *(We picked `StudentID` as Primary Key.)* |
| **3. Foreign Key (FK)** | A field in one table that **matches the Primary Key of ANOTHER table** in order to **link (join) the two tables together**! *(Can repeat multiple times in the "Many" table!)* | **`HouseCode`** inside `STUDENT` *(links to Primary Key `HouseCode` in the `HOUSE` table! Notice `H01` repeats for Aaliyah & Shanice!)* |
| **4. Secondary Key** | A non-unique field used frequently to **search, sort, or group records** (e.g. looking up students alphabetically or by location) — NOT required to be unique! | **`LastName`** or **`Parish`**! |

## 3. Database Field Data Types (Syllabus Objective 6.3!)

When creating a table in **Design View**, assigning the exact right **Data Type** saves storage and prevents invalid data entry!

| Official Data Type | Access / Base Name | What It Stores | **#1 Exam Watch-Out Trap!** |
| :--- | :--- | :--- | :--- |
| **Text** | Short Text / Long Text (Memo) | Letters, symbols, spaces, OR **digits you NEVER do math on** (`Name`, `Address`, **`PhoneNumber`**, **`TRN`**, **`StudentID`**, **`PostalCode`**)! | **TRAP!** ALWAYS store **`PhoneNumber`** (`876-555-0192`) and **`0045` IDs** as **TEXT**, NOT Numeric — Numeric strips leading zeros (`0045 → 45`) and rejects hyphens `-`! |
| **Numeric** | Number (Integer / Decimal) | Numbers used in **arithmetic calculations** (`Quantity`, `Age`, `ExamScore`, `UnitsSold`, `Weight`). | Pick **Integer/Long Integer** for whole numbers; **Single/Double** for decimals! |
| **Currency** | Currency | Monetary values (`Price`, `Salary`, `TuitionFee`, `Balance`) with automatic `J$` symbol & 2 decimal places! | Prevents rounding drift in financial calculations! |
| **Date / Time** | Date/Time | Calendar dates & clock times (`DateOfBirth`, `OrderDate`, `CheckInTime`). | Allows sorting chronologically and subtracting dates! |
| **Logical** | Yes/No *(Boolean)* | Fields with ONLY **two possible states** (`Yes/No`, `True/False`, `Paid?`, `InStock?`, `Scholarship?`)! | Displays as a clean tick-box `[✓]`! |

*(Modifying Table Structure: In **Design View**, you can safely **add new fields**, **delete unused fields**, or **change field properties** like `Field Size`, `Default Value`, `Required = Yes`, or `Validation Rule` — though changing a field from Text to Numeric can delete existing non-numeric entries!)*

## 4. Database Relationships & Joins (`1:1` vs `1:M` — Syllabus Obj 6.3!)

To link two tables cleanly in Access/Base (`Database Tools → Relationships`), **drag the Primary Key of the Parent ("One") table onto the matching Foreign Key of the Child ("Many") table** (both fields MUST share the **same Data Type**!).

1. **One-to-One (`1 : 1`) Relationship:**
   - Each single record in Table A matches **AT MOST ONE** record in Table B, and vice versa!
   - *Example:* One **Principal** leads ONE **School** (`PRINCIPAL 1 ─── 1 SCHOOL`), or one **Citizen** holds ONE **Passport** (`CITIZEN 1 ─── 1 PASSPORT`).
2. **One-to-Many (`1 : M` or `1 : ∞`) Relationship** *(Most common in exams & SBAs!)*:
   - One record in Table A can link to **ZERO, ONE, OR MANY** records in Table B — while each record in Table B belongs to **ONLY ONE** record in Table A!
   - *Example:* One **School House** (`H01 Red House`) has **MANY Students**, while each student belongs to ONLY ONE House (`HOUSE [1] ─── [∞] STUDENT`, joined via `HouseCode`)! Or one **Customer** places **MANY Orders** (`CUSTOMER [1] ─── [∞] ORDER`, joined via `CustomerID`)!

*(Enabling **Referential Integrity** prevents "orphan records" — e.g. Access stops a clerk from entering an Order for a fake `CustomerID` that doesn't exist in `CUSTOMER`, or deleting a Customer who still has active Orders!)*

## 5. Worked Example: Designing Two Linked Tables (Paper 2 Database Question!)

<WorkedExample
  title="Designing Tables, Data Types, Keys & Join for a Jamaican Bookshop Database"
  marks={10}
  problem={
    <>
      <strong>Island Reads Bookshop</strong> stores details of Suppliers and Books in two tables:
      <br />
      • <strong><code>SUPPLIER</code>:</strong> <code>SupplierID</code> (e.g. <code>SUP01</code>), <code>SupplierName</code>, <code>Telephone</code> (e.g. <code>876-555-2310</code>), <code>Parish</code>
      <br />
      • <strong><code>BOOK</code>:</strong> <code>ISBN</code> (e.g. <code>978-0134</code>), <code>Title</code>, <code>UnitPrice</code>, <code>QtyInStock</code>, <code>InPrint</code> (Yes/No), <code>DateAdded</code>, <code>SupplierID</code>
      <br />
      (a) State the MOST appropriate <strong>Data Type</strong> for: <code>Telephone</code>, <code>UnitPrice</code>, <code>QtyInStock</code>, <code>InPrint</code>, and <code>DateAdded</code>.
      <br />
      (b) Identify the <strong>Primary Key</strong> of <code>BOOK</code>, the <strong>Foreign Key</strong> inside <code>BOOK</code>, and the <strong>type of relationship</strong> between <code>SUPPLIER</code> and <code>BOOK</code> (one supplier supplies many books; each book comes from one supplier).
    </>
  }
  examTip="Never fall for the Telephone trap! Because Telephone numbers (876-555-2310) contain hyphens and are NEVER added or multiplied in arithmetic, their correct Data Type is ALWAYS Text (Short Text)!"
>

### (a) Appropriate Data Types
| Field | Data Type | Reason |
| :--- | :---: | :--- |
| **`Telephone`** | **Text** *(Short Text)* | Contains hyphens (`-`) and is never used in arithmetic calculations! |
| **`UnitPrice`** | **Currency** | Monetary selling price in J\$ requiring exact 2 decimal places. |
| **`QtyInStock`** | **Numeric** *(Integer)* | Whole count of books used in stock arithmetic. |
| **`InPrint`** | **Logical** *(Yes/No)* | Only two possible states (`Yes` or `No`). |
| **`DateAdded`** | **Date / Time** | Calendar date allowing chronological sorting. |

### (b) Keys & Table Relationship
- **Primary Key of `BOOK`:** **`ISBN`** *(uniquely identifies every single book!)*
- **Foreign Key inside `BOOK`:** **`SupplierID`** *(links back to Primary Key `SupplierID` in `SUPPLIER`!)*
- **Relationship Type:** **One-to-Many (`1 : M`)** from `SUPPLIER` (`1`) to `BOOK` (`∞`), joined on **`SupplierID`**!

</WorkedExample>
